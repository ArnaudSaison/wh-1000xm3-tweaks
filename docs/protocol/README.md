## How far to trust this

Each statement is one of these:

- **App code**: read directly from the decompiled app. This tells us what the app sends and expects. It is strong evidence for the wire format, but the app also supports many other models.
- **Inferred**: a reasonable reading that the code does not state outright. Marked where it occurs.
- **Confirmed on hardware**: seen working on a real WH-1000XM3 running firmware 4.5.2. See [04-verification.md](04-verification.md).
- **Unverified on the XM3**: anything that writes, except uploads. A voice package and a patched firmware have both worked on a real headset, including the update mode commands and the whole transfer.

The app shows only what it uses, so the firmware may accept commands the app never sends.

## Capturing the real protocol

Enable *Bluetooth HCI snoop log* in Android's Developer options, use the official app, then pull `btsnoop_hci.log` (usually through `adb bugreport`) and decode it:

```sh
uv run tools/btsnoop_mdr.py btsnoop_hci.log
```

## Corrections to earlier third-party notes

Against the app and the real headset:

| Earlier claim | Actual |
|---|---|
| Battery GET is `0x12` | GET `0x10`, RET `0x11`, NTFY `0x13`. `0x12` is not a command. |
| Escaping clears "top bits" | Only bit 4 is cleared: `3C/3D/3E` become `3D 2C/2D/2E`. |
| Protocol info reply is `01 00 70 00` | This headset replies `01 00 40 10`. |
| `0x11` in the NC effect field means "on in a SET" | It is `ADJUSTMENT_COMPLETION`; `0x10` is `ADJUSTMENT_IN_PROGRESS`. |
| Firmware reaches the headset by an unspecified Bluetooth path | CSR VM Upgrade over GAIA, on its own RFCOMM service. |
| The update download is plain HTTP, so an HTTP proxy is enough | The current app forces HTTPS. See [the update server section](03-firmware-update.md#the-update-server). |
